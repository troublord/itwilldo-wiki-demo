# Uncle Bob 不讀 AI 程式碼的關卡策略

## 精華重點

- Uncle Bob（Clean Code 作者）宣稱現在完全不讀 agent 寫的程式碼，這是他吃到 agent 生產力的唯一方法
- 信心來源從「人看過」換成「機器測過」：單元測試、Gherkin 測試（Specification by Example）、QA 程序、品質指標、mutation testing、測試涵蓋率
- Mutation testing 是關鍵一環：故意把程式碼改壞，看測試套件抓不抓得到，用數字驗證「測試本身可不可信」
- 三週前他自己也承認：多數時候只用單元測試加粗略檢查就夠，Gherkin/QA 這些他猜大專案才划算，且「還在驗證中」——關卡沒有固定套餐，依案子大小輕重裝
- 反對意見中最有份量的兩條：
  1. 「你設計測試的時候就已經在間接看程式碼了，真的什麼都不看等於沒在測」——但這其實抓到語病，他放掉的只是實作細節，測試設計與維護他仍深度介入
  2. 「實作和測試都是同一個 agent 寫的，兩邊可能錯得一致，看過太多 AI 測試只是在模仿被測程式碼、甚至測到 mock」——這是真問題；mutation testing 抓得到「測試太弱」，但抓不到「規格本身理解錯了」
- 核心洞察：這套關卡是被「六十年經驗的判斷力」設計出來的——哪裡該設檢查、mutation 分數多少算夠、Gherkin 案例要涵蓋哪些邊界，都是判斷力的產物。資淺工程師照抄「不讀碼」的結論但沒有那套判斷力，拿到的只有風險

## 延伸討論：個人要做到「不讀程式碼」的考驗

若要在自己還沒太多開發經驗的情況下，日後也想達到這種效果，「不讀程式碼」換來的不是「不用懂程式」，而是「懂的地方換了」——從讀懂實作細節，換成設計驗證機制，這個轉換對零開發經驗的人反而更難。三層具體考驗：

1. **規格判斷力**：寫 code 之前要能準確講出「對的行為是什麼、邊界案例有哪些」（Gherkin/acceptance criteria 的基礎）。沒寫過程式的人很難有這種直覺，因為不知道魔鬼藏在哪個細節。
2. **測試品質判斷力**：要能一眼看出一份測試是不是在模仿被測程式碼、是不是測到 mock 而非真行為。這通常得自己寫過夠多爛測試、踩過坑才練得出嗅覺。Mutation testing 抓「測試太弱」，抓不到「規格理解錯了」——這一層還是要靠人。
3. **出事時的兜底能力**：關卡再嚴，系統終究會在意料外的地方壞掉，那一刻沒有 debug 地基的人只能臨時硬讀——專業知識決定救不救得回來。

## 我的想法：借用別人的 skills 加速

未來要達到這件事，比較明智的做法是大量參考別人已經分享出來的做法——例如導入別人整理好的 skills 去跟 AI 合作，測試品質、規格判斷這類東西，網路上已經有人在分享。單靠個人知識與經驗，在這個時代不太明智，而且太慢。

## Claude 的反駁

借用別人的 skills 是加速器，但有兩個地方會失靈：

1. **別人的關卡是為別人的系統校準的**。Uncle Bob 敢設 mutation testing 門檻、敢定 Gherkin 案例邊界，是因為那套判斷來自他自己踩過的坑。導入別人的「好測試該長什麼樣」skill，拿到的是判斷結果，不是判斷力本身——換了系統、換了風險屬性可能完全套不上，而要有基本判斷力才知道「這裡套不上」。沒那個底子，連被套錯都不知道。
2. **這呼應了文章裡最痛的反駁**：「同一個 agent 寫實作又寫測試，兩邊可能錯得一致」。如果很多人都用同一份熱門 skill 餵給 AI，大家的盲點也會是同一個盲點——這是一種相關性很高的系統性風險,跟「每個人靠自己經驗、盲點各不相同」正好相反。借來的判斷力規模化很快，錯的地方也規模化很快。

結論：借 skills 可以省掉「從零建立每一種判斷力」的時間，比單靠個人經驗快，這點沒錯。但它是墊底加速，不是替代品——仍需要一點自己的實戰經驗，才有資格核對「這個借來的框架套在我的案子上到底對不對」。完全外包判斷，跟「完全不讀程式碼」是同一種風險：信心建立在別人設計的東西上，卻沒人替你檢查那個設計本身有沒有問題。

## 一句話評論

> 關卡能借，判斷力借不到——借來的框架規模化多快，借來的盲點就規模化多快。
