# 工作判斷模式庫

> 這份筆記整理我在工作中反覆使用的判斷模式、決策原則與技術排查方法。

---

## 核心工作方式

- **正確性，而不是表面能跑**
- **影響範圍，而不是只改眼前一行**
- **可驗證性，而不是憑感覺猜**
- 先縮小問題範圍，再選最小必要改動

---

## 可重複使用的 Patterns

### Pattern 1：先確認執行鏈路，再修改設定

**適用**：Maven、Spring Boot、properties、profile、generated resources 互相影響時

**步驟**：
1. 列出實際執行指令
2. 確認 active profile
3. 確認 build 階段產生哪些檔案
4. 確認 run 階段 classpath 讀哪些檔案
5. 最後才改 properties 或指令

**常見錯誤**：一開始就補 key，會掩蓋真正問題

---

### Pattern 2：最小必要改動

**適用**：已有可運作流程，某一段出問題

**原則**：只改一個環節。先改 build，就暫時不要改 run。驗證後再決定是否需要第二步。

---

### Pattern 3：修改共用資源前先做影響範圍搜尋

**適用**：修改 i18n、共用 constants、shared config、common fields

**搜尋清單**：
- [ ] 完整 key
- [ ] 短 key
- [ ] 原始文案值
- [ ] 解構後名稱
- [ ] alias / 轉接引用
- [ ] 測試檔與 snapshot
- [ ] route/page 關聯

---

### Pattern 4：用「兩種寫法差異」學技術概念

把兩種寫法並列，問它們在資料結構、命名、型別、執行結果、可讀性上的差異。

---

### Pattern 5：不確定流程時先確認狀態（Git/MR）

先確認 MR 是 open、approved、merged 還是 closed，再判斷下一步。

**決策紀錄**：MR 通過後又有修改 → 開新分支處理，保留清楚審查邊界。

---

### Pattern 6：本地 workaround 與正式解法分離

1. 先用本地 workaround 解決當下阻塞
2. 不要立刻推送不屬於自己範圍的設定變更
3. 若問題具有共通性，再整理原因並與團隊討論正式解法
4. **要記錄 workaround**，避免未來忘記本地環境和版本庫不同

---

### Pattern 7：先恢復可運行，再追根因

**第一層**：當下怎麼恢復可跑
**第二層**：正式應該怎麼查

---

## 重要決策紀錄

### Maven / Spring Boot 本地啟動問題（2026-04-15）

**問題**：`Could not resolve placeholder 'cache.mode'`，properties 明明有寫

**根因**：properties 重複內容導致讀取異常（${env} 自動產生資料夾干擾）

**解法**：
1. 將 pom 中會改動檔案的部分在本地註解（不推 Git）
2. 將 common、dev properties 合併到 dev properties
3. 調整 clean package，其他 run/build 流程維持原樣

**教訓**：本地 workaround 不等於正式解法

---

### GitLab MR 後續修改（2026-04-20）

**情境**：某分支 MR 已通過，又有新修改

**決定**：開新分支處理

**理由**：保留原 MR 審查邊界，避免把已通過內容和新修改混在一起
