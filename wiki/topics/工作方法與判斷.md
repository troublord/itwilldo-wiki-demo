# 工作方法與判斷

工作與生活中會反覆用到的判斷框架、決策原則、技術排查方法論——收的是可重複套用的「判斷力」本身，不是單一專案的操作紀錄或臨時決定。

## 技術排查與工作決策的 Pattern 庫

**來源**：使用者自己整理的工作筆記，完整內容見 `raw/工作判斷模式庫.md`

**核心工作方式**：
- 正確性，而不是表面能跑
- 影響範圍，而不是只改眼前一行
- 可驗證性，而不是憑感覺猜
- 先縮小問題範圍，再選最小必要改動

**幾個常用 Pattern**：
- **先確認執行鏈路，再修改設定**：遇到 Maven/Spring Boot/properties/profile 互相影響時，先列出實際執行指令、確認 active profile、確認 build/run 階段各自讀哪些檔案，最後才改設定——一開始就補 key 容易掩蓋真正問題。
- **最小必要改動**：已有可運作流程、某一段出問題時，只改一個環節，驗證後再決定要不要動下一步。
- **改共用資源前先做影響範圍搜尋**：改 i18n、共用 constants、shared config 前，要搜完整 key、短 key、原始文案值、解構後名稱、alias、測試檔與 snapshot、route/page 關聯。
- **本地 workaround 與正式解法分離**：先用本地 workaround 解除當下阻塞，但不要順手把不屬於自己範圍的設定變更推上去；如果問題有共通性，再整理原因跟團隊討論正式解法；workaround 一定要記錄下來，避免以後忘記本地環境跟版本庫不一致。
- **先恢復可運行，再追根因**：分兩層，第一層先讓當下能跑，第二層才正式去查根本原因。
- **不確定流程時先確認狀態**：例如 MR 是 open/approved/merged/closed，先確認狀態再判斷下一步；MR 通過後又有修改，開新分支處理，保留清楚的審查邊界。

## 唯一主線法則：每段工作時間只挑一件事推進

**來源**：使用者自己的框架，完整內容見 `raw/框架｜唯一主線法則.md`

- **選主線的判準**：時間壓力 > 精力 > 重要性——選的是「今晚最值得推進的一件事」，不是「今晚最容易成功的一件事」。
- **決定時機**：最適合在喝咖啡的過程中決定，不會太早脫離當天狀態，也不會太晚讓空檔被娛樂吃掉。
- **小成果的判準**：可以接受小成果，但至少要滿足其中一項——把模糊的東西變清楚、補到明天可用的素材、產出明天可接續的待辦、讓明天更容易開始。
- **成功/失敗判準**：當天有一件事被打勾、且能幫助明天接續，就不算白過；當天沒有任何事項被打勾，才算絕對失敗。

## Uncle Bob 不讀 AI 程式碼的關卡策略

**來源**：Uncle Bob（Robert C. Martin）推文與網路討論，完整摘要見 `raw/links/參考｜Uncle Bob 不讀 AI 程式碼的關卡策略.md`

- Uncle Bob 宣稱現在完全不讀 agent 寫的程式碼，這是他吃到 AI 生產力的方法。信心來源從「人看過」換成「機器測過」：單元測試、Gherkin 測試、QA 程序、品質指標、mutation testing（故意把程式碼改壞，看測試套件抓不抓得到，驗證測試本身可不可信）。
- 這套關卡不是固定套餐，是依案子大小輕重裝的——他自己也承認多數時候只用單元測試加粗略檢查就夠。
- 最有份量的反對意見：實作和測試常常是同一個 agent 寫的，兩邊可能錯得一致——這抓得到「測試太弱」，但抓不到「規格本身理解錯了」。
- 核心洞察：這套關卡是被「六十年經驗的判斷力」設計出來的——哪裡該設檢查、mutation 分數多少算夠，都是判斷力的產物。資淺工程師照抄「不讀碼」的結論但沒有那套判斷力，拿到的只有風險。
- 借用別人已經設計好的關卡（例如別人分享的 skills）可以加速，但有兩個地方會失靈：一是別人的關卡是為別人的系統校準的，拿到的是判斷結果不是判斷力本身；二是如果很多人都用同一份熱門 skill，大家的盲點也會是同一個盲點——借來的判斷力規模化多快，借來的盲點就規模化多快。

> 關卡能借，判斷力借不到——借來的框架規模化多快，借來的盲點就規模化多快。

## 這幾則的共通點

三則都在講同一件事的不同面向：**可靠的判斷力來自親自踩過的經驗，不能靠抄結論、套用別人的框架完全取代**——工作 pattern 庫裡「workaround 要記錄、不能忘記本地環境跟版本庫不一致」，唯一主線法則裡「選主線要盯著當下狀態、不是套死公式」，跟 Uncle Bob 那篇「借來的判斷力規模化多快、盲點就規模化多快」，都是同一個底層邏輯。
